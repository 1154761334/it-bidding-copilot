# 多 AI 协作与开发日志规范

本文档用于约束本项目后续的连续开发方式，避免在多代理协作下再次出现“代码、文档、测试、页面状态互相漂移”。

## 1. 当前协作背景

当前项目由多个 AI 工具协作开发，主要分工如下：

- `Codex`：方案收敛、代码审查、状态核对、关键实现、文档治理
- `Antigravity / Gemini Flash`：承担复杂但开发量大的实现任务
- `OpenCode`：当前不是主力通道，可忽略

由于 `Codex` 配额较宝贵，推荐的工作方式不是让单一代理持续盲写，而是：

1. 先由 `Codex` 梳理目标、约束和方案
2. 再把大块实现交给 `Antigravity / Gemini Flash`
3. 最后回到 `Codex` 做代码核对、进展审查、文档修正和验收

## 2. 产品主目标

本项目的产品目标不是通用文档工具，而是面向政企 IT 招投标场景的标书自动生成系统。当前主线应始终围绕以下流程推进：

1. 企业资质材料导入、自动识别、人工复核、结构化入库
2. 招标文件解析，提取硬要求、软要求、评分项、废标项、模板等关键信息
3. 用户确认投标主体、补充项目资料、选择或确认资质/人员/案例
4. 基于招标文件模板与企业材料，完成多轮 AI 辅助编标
5. 用户复核、终审、导出最终投标文件

如果后续新增功能不能明确支撑这条主线，应默认降级优先级。

## 3. 每轮开发的最低动作

后续不再要求每轮都写长日志，统一改成轻量规则：

1. 日常小改动：优先通过 GitHub commit / PR 留痕
2. 中等改动：更新 `docs/current_status.md` 或相关状态文档
3. 重大改动：更新状态文档，并在 `docs/development_logs/` 新增一篇日志

其中“重大改动”通常指：

- 新增或删除主流程接口
- 页面职责变化
- 服务返回结构变化
- 测试基线明显变化
- 运行方式、默认模型、数据流发生变化

禁止在下面这些情况下只改代码不改文档：

- 新增或删除接口
- 页面职责变化
- 服务返回结构变化
- 测试基线变化
- 运行方式、默认模型、数据流发生变化

## 4. 开发日志要求

开发日志目录：`docs/development_logs/`

建议命名：

- `YYYY-MM-DD-agent-name.md`

示例：

- `2026-04-09-codex.md`
- `2026-04-09-gemini-flash.md`

日志只记录关键轮次，不要求每次开发都写。

每篇日志至少包含：

- 开发时间
- 开发代理 / 执行者
- 本轮目标
- 主要改动
- 涉及文件/模块
- 验证结果
- 风险与遗留问题
- 对下一轮的建议

## 5. GitHub 与本地文档的分工

推荐采用“GitHub 为主，本地核心文档为辅”的方式：

- `GitHub`：负责 commit、PR、review、讨论、变更留痕
- 本地 `docs/`：负责当前真实状态、产品主线、协作规则、关键交接信息

当前默认保留的核心文档：

- `docs/current_status.md`
- `docs/feature_inventory.md`
- `docs/development_workflow.md`

`docs/development_logs/` 只记录关键轮次，不作为日常开发的强制动作。

## 6. 交接时优先阅读顺序

新一轮开发开始前，默认按下面顺序建立上下文：

1. `docs/current_status.md`
2. `docs/feature_inventory.md`
3. `docs/development_workflow.md`
4. 如近期有关键轮次，再看 `docs/development_logs/` 下最近 1-3 篇日志
5. 视任务需要再读 `docs/frontend_backend_alignment.md`、`docs/main_flow_task_list.md`

## 7. Codex 适合做什么

优先交给 `Codex` 的工作：

- 方案设计与路径收敛
- 架构和模块边界判断
- 文档与代码一致性校对
- 关键服务层修复
- 回归验证与验收

## 8. Gemini Flash 适合做什么

优先交给 `Antigravity / Gemini Flash` 的工作：

- 大段前端页面实现
- 重复性较高的 CRUD、表单、展示层开发
- 明确边界内的批量代码改造
- 基于既定方案的接口接线和页面收尾

前提是：任务边界必须先由 `Codex` 或人工明确。

## 9. 当前主要风险

截至本轮文档更新时，当前项目的主要风险不是“没有方向”，而是“已有实现的契约漂移”：

- 文档和代码口径不完全一致
- 前端类型和后端真实返回结构存在偏差
- 历史联调结论不能直接代表当前可回归状态
- 后端服务层已有回退，测试基线失真

因此，后续几轮开发应优先恢复“可信状态”，再继续大规模扩展功能。
