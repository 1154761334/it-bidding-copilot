# 解析质量门槛

本文档用于明确一个原则：

- “能解析出结果” 不等于 “可实战使用”

当前项目后续对“企业资质解析”和“采购文件解析”的验收，不再以是否有 JSON 输出为主，而以是否能直接支撑投标动作、是否能显著降低人工整理成本为主。

## 1. 总原则

实战可用至少要满足三条：

1. 主要信息抽对，不能把关键内容大量抽错
2. 抽出的结构能直接进入下一步，不需要整页重做
3. 系统能明确暴露不确定项，方便人工补核，而不是悄悄给出看似完整但错误的结果

## 2. 企业资质解析质量门槛

### 2.1 目标

企业资质解析的目标不是“把商务技术文件拆碎”，而是：

- 从多种材料中沉淀可复用的企业资产
- 为后续偏离矩阵、素材包、章节生成提供可信输入

### 2.2 最低可用标准

对一份典型商务技术文件，至少要做到：

1. 能稳定识别并入库核心证书
2. 能识别关键历史案例
3. 能识别关键人员与对应社保证明
4. 能保留图片证据和来源关系
5. 支持重复导入去重

### 2.3 重点看什么

比起数量，更看这些质量信号：

- 证书名称是否准确
- 是否把“功能说明 / 页面截图 / 流程图”误识别成证书或人员
- 人员姓名是否像真实姓名，而不是“方式”“程图”这类噪声
- 授权书中的身份证号、手机号是否被误提成错误字段
- 案例是否真的是“历史业绩”，而不是当前投标项目本身
- 图片证据是否能挂到证书 / 社保 / 授权等资产上

### 2.4 不可接受的情况

以下情况出现任意一项，都不能算“实战可用”：

- 核心证书大面积漏抽
- 大量把方案说明错当成资质
- 人员姓名明显失真
- 图片证据未注册或与结构化资产失联
- 重复导入后生成大量重复资产

### 2.5 当前观察

当前链路已具备：

- 商务技术文件解析
- LLM 标准化
- 去重
- 图片证据注册
- 证书 / 案例 / 人员 / 授权 / 社保入库

当前仍需继续打磨：

- 人员抽取精度
- 案例抽取泛化
- 字段归一化深度
- 多格式样本，尤其是 PDF 的实测覆盖

## 3. 采购文件解析质量门槛

### 3.1 目标

采购文件解析的目标不是“把文档拆成 requirement 列表”，而是：

- 为项目建档提供可信基础信息
- 为偏离矩阵提供可编辑但基本可靠的原子要求
- 为后续生成和审标提供评分项、废标项、证明材料要求

### 3.2 最低可用标准

对一份典型采购文件，至少要做到：

1. 项目名称、预算、截止日尽量准确
2. 评分项能抽出来
3. 废标项 / 红线项能抽出来
4. 资格类、技术类、商务类要求有基本分类
5. 证据材料要求尽量抽出来
6. 结果可以直接进入人工确认工作台

### 3.3 重点看什么

真正有实战价值的不是总条数，而是：

- 评分项是否漏掉关键高分项
- 废标项是否漏掉关键红线
- requirement 是否被公告、报名流程、背景介绍污染
- section / clause 映射是否可回溯
- 证据材料要求是否对后续资质匹配有帮助
- 不能确认的内容是否能进入 warning，而不是硬装作正确

### 3.4 不可接受的情况

以下情况出现任意一项，都不能算“实战可用”：

- 高价值评分项明显缺失
- 红线项大量漏抽
- requirement 里充满招标公告、报名方式、联系人等噪声
- 预算 / 截止日 / 项目名错得离谱且没有 warning
- 新解析任务经常失败，只能依赖历史项目结果

### 3.5 当前观察

当前链路已具备：

- 真实采购文件解析
- quality check
- requirement 分类
- 偏离矩阵输入
- Go/No-Go 基础结果

当前仍需继续打磨：

- requirement 噪声继续收紧
- 资产匹配解释力
- Go/No-Go 可信度
- 多样格式样本，尤其是 PDF / 扫描件

## 4. 后续验收方式

后续不再只报“通过 / 不通过”，而要同时报这四类信息：

1. 样本文档
2. 核心结果数量
3. 明显误报 / 漏报
4. 对主流程的真实影响

建议后续每次解析能力变更，至少给出：

- 企业资质样本 1 份以上
- 采购文件样本 1 份以上
- 是否支持 Word / PDF
- 人工补核需要花多大力气

## 5. 当前执行策略

在主流程优先级上，先做：

1. 企业资质解析质量打磨
2. 采购文件解析质量打磨
3. 多公司 / 多项目上下文

之后再继续深入编标和终审自动化。
