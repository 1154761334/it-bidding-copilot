# Opus 协作总方案

本文档用于给外部协作者快速理解当前项目的产品规划、开发进度、技术路线、关键问题与下一步建议。

目标不是重复零散状态，而是把当前项目收敛成一份可供继续联合研发的工作底稿。

## 1. 项目定位

项目名称：

- IT Bidding Copilot

项目目标：

- 面向政企 IT 投标场景，建立从企业资质建库、采购文件识别、偏离矩阵确认、章节生成、红队审标到最终导出的完整工作流。

当前主基线：

- 前端：React + Vite
- 后端：FastAPI
- 数据库：PostgreSQL + pgvector
- 接口前缀：`/api/v1/*`

当前产品主线：

1. 企业资料建库
2. 新建投标项目
3. 起草前素材确认
4. 在线编标工作台
5. 审标与导出

## 2. 当前产品规划

## 2.1 目标产品形态

理想中的产品不是若干松散页面，而是一条完整业务流：

### A. 企业资料建库

- 上传既往投标文件、资质文件、案例、人员简历、图片证据
- AI 自动识别证书、案例、人员、授权、社保、图片证据
- 归属于一个企业主体
- 前端回显识别结果
- 人工确认、修正、删除、补录
- 最终形成企业资产库

### B. 新建投标项目

- 新建项目并上传采购文件
- 自动提取：
  - 项目名称
  - 项目编号
  - 预算
  - 截止时间
  - 资格要求
  - 技术要求
  - 评分项
  - 废标项
  - 证明材料要求
- 前端回显并允许人工修正
- 确认后形成正式投标项目

### C. 起草前素材确认

- 从企业资产库中选择或智能推荐：
  - 资质
  - 案例
  - 人员
  - 图片证据
- 上传项目专属补充材料
- 形成“项目素材包”
- 人工确认后进入起草阶段

### D. 在线编标工作台

- 左侧：大纲与章节树
- 中间：正文编辑器
- 右侧：证据链、AI 建议、审稿反馈
- 支持：
  - 单章生成
  - 整项目生成
  - 重试未完成章节
  - 手工改稿
  - AI 改写/补强/压缩/对齐评分点

### E. 审标与导出

- 红队审标
- 风险与缺证据提示
- 导出前检查
- 导出最终 Word

## 2.2 当前产品判断

当前系统已经满足：

- 主流程闭环
- 真实文档联调
- 浏览器自动化回归
- 持续开发基础

但尚未完全达到：

- 正式交标成品级体验
- 正式交标成品级版式与导出质量

## 4. 当前关键技术思路

## 4.1 主业务架构

当前整体架构保持简约，不继续引入重型多智能体编排框架：

- 前端负责流程表达与交互确认
- 后端负责业务编排、状态推进、数据落库
- LLM 只参与高价值语义节点
- 数据库存放项目、资产、草稿、审标和 trace

设计原则：

- 主链路先可用
- 高风险节点再加多轮校验
- 不让模型直接裸写库

## 4.2 当前 AI 使用方式

当前 AI 主要用于：

- 企业资质标准化
- 采购文件语义识别
- 查询重写
- 章节写作
- 审计与润色

整体采用轻量多轮模式：

- `Extractor`
- `Reviewer`
- `Resolver`

并保留 deterministic fallback，避免因为单次模型不兼容而阻断整条链路。

## 4.3 文档解析思路

当前已经明确：

- 大模型不能直接可靠地“裸读 Word”
- 投标文件与采购文件必须先经过结构解析，再进入语义抽取

当前推荐方向：

- `DOCX/PDF 主解析`：`MinerU`
- `Word 薄辅助层`：`OOXML/python-docx`
- `图片证据`：OCR
- `字段抽取`：LLM

不是为了堆技术，而是为了同时满足：

- docx 读取
- 章节树恢复
- 表格提取
- 图片证据提取
- 最终 Word 回写导出

详细设计见：

- [document_parsing_stack_design.md](/root/it-bidding-copilot/docs/document_parsing_stack_design.md)

## 5. 当前存在的主要问题

## 5.1 产品层问题

### 1. 企业建库确认还不够强

虽然已有“最近导入批次”和“企业建库确认”区，但还不是完整的批次级确认工作台。

缺口：

- 批次级回退
- 批次级确认
- 批次级差异视图

### 2. 采购文件确认界面还不够细

当前 `/rfp` 已支持确认建档，但还没有拆成真正适合人工审查的分步确认界面。

缺口：

- 评分表确认区
- 资格要求确认区
- 技术要求确认区
- “确认建档”与“仅预览”更清晰的状态区分

### 3. 编标工作台还未完全成型

当前已支持在线改稿，但还缺：

- 选区 AI 改写
- 整章补强/压缩
- 版本回看
- 更成熟的 Markdown 编辑器工作台

### 4. 导出质量还未完全达到正式交付级

当前已可导出、已能带证据图片，但仍缺：

- 模板保样式增强
- 正文中更精确的图片插入位置
- 更接近正式投标件的版式

## 5.2 技术层问题

### 1. 文档解析栈还未正式统一

当前项目已有：

- `python-docx`
- `docling`
- 自定义规则切块

但统一门面层尚未抽出。

影响：

- 解析逻辑分散
- 不利于接入 `MinerU`
- 不利于后续定位不同解析器的质量差异

### 2. 采购文件泛化能力仍需继续打磨

当前已经不是写死模板，但仍然存在：

- requirement 噪声
- 不同招标文件结构差异
- 评分表表达差异
- 隐性废标项识别不稳定

### 3. 企业资产数据治理仍未完全收口

当前已补：

- 二次清洗
- 去重
- 实名人员拆解

但仍存在：

- 发证单位等字段不统一
- 图片与文本证据的绑定粒度还可提升

### 4. 向量检索仍处于降级可用状态

当前为了先保主链路，未配置兼容 embedding 模型时会静默降级。

这使系统可用，但不是最终生产态。

## 5.3 运行与协作层问题

### 1. 新旧进程切换曾出现误命中旧代码

已经修过一次，但这说明：

- 启动方式和进程治理仍需更清晰

### 2. 页面仍有少量“半产品化”入口

虽然已经清理了不少重复页面，但部分入口与页面职责仍需进一步收口。

## 6. 当前几条路线思考

## 6.1 是否应该继续优先打磨主流程

结论：

- 应该

原因：

- 这个项目不是内容平台，而是投标生产工具
- 只有主流程成立，页面优化和高级能力才有意义

所以当前最优先的是：

1. 企业建库确认
2. 采购文件确认建档
3. 项目素材包确认
4. 在线编标
5. 审标与导出

## 6.2 是否应该重型多智能体化

结论：

- 不应该

建议：

- 保持单主流程
- 在高风险节点做轻量多轮校验

原因：

- 全链路重型 Agent 编排会提高复杂度和调试成本
- 当前更需要的是稳定、可追踪、可落库

## 6.3 是否应该把文档识别全交给某一个库

结论：

- 不建议完全交给单个库

更稳的方式是：

- `MinerU` 做主解析增强
- 保留薄的 Word 原生辅助层
- OCR 单独处理图片证据

## 7. 推荐开发顺序

## 7.1 短期优先级

### P0

1. 抽统一解析门面层
2. 接入 `MinerU` 主解析路径
3. 接入 OCR 处理图片证据
4. 继续打磨采购文件确认建档工作台
5. 继续增强项目素材包的推荐理由与证据预览
6. 把在线编标工作台继续做成真正可用编辑器

### P1

1. 企业建库确认批次工作台
2. 采购文件历史报告页
3. 审标页证据链表达统一
4. 设置页推荐配置优化

### P2

1. 审标后自动修复闭环
2. 模板保样式导出增强
3. 正文精确图片插入
4. Excel 导出
5. 章节版本管理

## 7.2 更适合的实施阶段

### Phase A：解析层统一

- 抽 `document_parse_service`
- 统一内部输出 schema
- 为接 `MinerU` 做准备

### Phase B：项目建档确认增强

- 采购文件确认界面分层
- 明确评分/资格/技术三类审查入口

### Phase C：编标工作台增强

- Markdown 编辑器工作台
- AI 改写与版本回看

### Phase D：成品导出增强

- 模板样式
- 图片位置
- 最终交付版式

## 8. 建议外部协作者优先关注的问题

如果由外部协作者参与，最值得优先研究和投入的点是：

1. 文档解析门面设计是否足够稳
2. `MinerU + OCR + LLM` 的职责边界是否还可进一步简化
3. 采购文件确认建档界面如何拆成更高效的人工复核流程
4. 编标工作台应选用哪个开源 Markdown 编辑器改造
5. 导出成品如何在不引入过高复杂度的前提下提升版式质量

## 10. 总结

当前项目已经过了“能不能做成”的阶段，进入了“如何把它做成更稳、更像正式产品”的阶段。

可以明确的判断是：

- 主流程已经成立
- 页面产品化大体成立
- 导出和解析层仍是最值得继续投入的核心区

这意味着后续开发不应再发散，而应继续沿着：

- 解析层统一
- 项目建档确认
- 编标工作台增强
- 成品导出增强

这四条线稳定推进。
